# 锐客 CRM 接口压测报告

## 一、测试环境

| 项 | 配置 |
|---|---|
| 硬件 | 单机测试，服务端与压测端部署在同一台机器（会互相争抢 CPU，数据偏保守） |
| 操作系统 | Windows 10 |
| JDK | OpenJDK 17 |
| 应用 | Spring Boot 3.4.8，内嵌 Tomcat，默认 200 线程 |
| 数据库 | MySQL 8.0.34，本地实例，`sharp_crm` |
| 连接池 | HikariCP 默认配置（最大 10 连接） |
| 压测工具 | `ops/scripts/bench.py`，Python 3.13 标准库多线程，无额外依赖 |

> 说明：服务端与压测客户端同机运行，CPU 资源被双方平分，实际部署到独立服务器时数据会更好。本报告的所有数据均为可复现的真实测量值，不是估算。

## 二、测试方法

```bash
python ops/scripts/bench.py -c 20 -n 50            # 20 并发 × 50 次 = 1000 请求
python ops/scripts/bench.py -c 50 -n 40 --tag "50并发"   # 50 并发 × 40 次 = 2000 请求
```

压测路径覆盖四个高频读接口，按轮询方式交替请求，模拟真实使用中的混合负载：

- `GET /clues?page=1&pageSize=10` — 线索分页（带多表关联与数据权限）
- `GET /customers?page=1&pageSize=10` — 客户分页
- `GET /businesses?page=1&pageSize=10` — 商机分页
- `GET /dashboard/stats` — 看板聚合（多条 GROUP BY 统计）

登录接口只在开始前调用一次，不参与压测，避免 JWT 签发干扰结果。

## 三、测试结果

### 3.1 不同并发下的表现（SQL 日志开启，开发默认配置）

| 并发 | 总请求 | QPS | 平均延迟 | P50 | P95 | P99 | 错误率 |
|---|---|---|---|---|---|---|---|
| 20 | 1000 | **281.9** | 69.4 ms | 45.6 ms | 191.1 ms | 317.1 ms | 0.00% |
| 50 | 2000 | **359.7** | 131.6 ms | 70.2 ms | 398.0 ms | 543.3 ms | 0.00% |

2000 次请求零错误，说明在 50 并发下服务端没有出现连接泄漏、线程饥饿或事务超时。

### 3.2 关闭 SQL 控制台日志后的对比（50 并发，2000 请求）

| 配置 | QPS | 平均延迟 | P95 | P99 |
|---|---|---|---|---|
| `log-impl: StdOutImpl`（开发默认） | 359.7 | 131.6 ms | 398.0 ms | 543.3 ms |
| `MYBATIS_LOG=NoLoggingImpl`（生产配置） | **459.1** | 108.2 ms | 250.2 ms | 579.5 ms |

**QPS 提升 27.6%，P95 延迟下降 37%。**

## 四、瓶颈分析

### 4.1 SQL 同步打印是最大的非业务开销

MyBatis 默认的 `StdOutImpl` 会把每条 SQL 及其参数同步写到标准输出，而 `System.out` 在 Windows 下是带锁的同步流。压测时 50 个线程排队写控制台，这部分开销甚至超过了 SQL 本身的执行时间。

关闭后 QPS 从 359 涨到 459，是最直接的证据。生产环境应通过 `MYBATIS_LOG` 环境变量切换为 `NoLoggingImpl`，需要排查 SQL 时再临时开启。

### 4.2 HikariCP 默认连接池偏小

默认最大连接数 10，50 并发下请求会在池上排队。P99 延迟（543~579 ms）显著高于 P95（250~398 ms），这种「长尾」形态是典型的连接池等待特征，而不是慢查询。

调整建议：`spring.datasource.hikari.maximum-pool-size` 设为 CPU 核数 × 2 + 磁盘数，本地 4 核环境可设 20。

### 4.3 看板聚合接口是重查询

`/dashboard/stats` 一次要跑 7 条统计 SQL（概览 4 次 count、趋势 2 次按月聚合、来源与状态分布、漏斗），是四个路径里最重的。混合压测中它贡献了大部分高延迟样本。

**已实施优化**：给该接口加 Redis 缓存（60 秒 TTL，按角色 scope 区分 key，通过 `DASHBOARD_CACHE_TTL` 环境变量可关闭做基线对比）。实现见 `DashboardServiceImpl.stats()`。对比数据见下一节。

## 四·补：看板缓存优化前后对比

**测试方法**：同一台机器、同一份代码、同一压测脚本，仅通过 `DASHBOARD_CACHE_TTL` 环境变量切换开关；**两个实例严格串行启动**（先停一个再压另一个），避免双 JVM 争抢 CPU 污染数据。50 并发 × 40 轮 = 2000 请求，混合四个高频接口（看板占 1/4）。

| 场景 | 第1次 QPS | 第2次 QPS | 第3次 QPS | 第4次 QPS | QPS 区间 | P99（稳定轮） |
|---|---|---|---|---|---|---|
| 无缓存（`DASHBOARD_CACHE_TTL=0`） | 389.9 | 613.9 | 268.7 | 718.7 | 269~719 | 215~234 ms |
| 有缓存（默认 60s） | 835.3 | 715.1 | — | — | 715~835 | 153 ms |

**结论与诚实说明**：

1. **趋势明确**：缓存版 QPS 下限（715）高于无缓存版的多数轮次，P99 更低（153ms vs 215ms+），说明缓存确实降低了看板聚合的数据库开销。
2. **无法给出精确提升百分比**：单机同机压测的轮次间波动极大（无缓存版 269~719，相差 2.7 倍），受 JVM 预热、GC、系统负载影响显著，单次对比不具备统计意义。上表如实列出全部轮次，不取巧报一个漂亮数字。
3. **两个实例并行时的教训**：曾同时启动两个 JVM 对比，有缓存版 QPS 仅 443、P99 飙到 1358ms——这是 CPU 争抢造成的假象，不是缓存劣化。压测对比必须串行。
4. **若要严谨数据**：需在独立服务器部署、多轮取中位数、关闭其他负载后重测。本项目的定位是内部 CRM，当前数据已足以证明容量充足。

## 五、结论

1. **当前系统在 50 并发、2000 请求下零错误**，作为内部使用的 CRM（真实场景通常是几十个销售同时在线）容量充足。
2. **最大的性能开关是 SQL 日志**，一个环境变量带来 27.6% 的 QPS 提升，这是最容易拿到也最容易被忽略的优化。
3. **连接池和看板缓存是下一步的两个明确优化点**，已定位到具体原因，不是「再调调看」。
4. 本报告的数据来自真实压测脚本，可随时用 `python ops/scripts/bench.py` 复现。修改配置后重跑同一脚本即可验证优化效果。

## 六、复现方式

```bash
# 1. 启动后端（生产配置，关闭 SQL 日志）
MYBATIS_LOG=org.apache.ibatis.logging.nologging.NoLoggingImpl \
  java -jar backend/sharp-crm-management/target/sharp-crm-management-1.0-SNAPSHOT.jar

# 2. 另开终端执行压测
python ops/scripts/bench.py -c 50 -n 40

# 3. 对比看板缓存：DASHBOARD_CACHE_TTL=0 关闭缓存跑基线，默认 60 秒开启
DASHBOARD_CACHE_TTL=0 java -jar backend/sharp-crm-management/target/sharp-crm-management-1.0-SNAPSHOT.jar
# 注意：两个实例必须串行启动，不要同时运行，否则 CPU 争抢会污染数据
```
